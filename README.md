# CPC Optimizer — Customer Allocation Models

This repo contains LP-based allocation models for distributing a constrained supply of product across customers. Each model lives in its own folder with its own `main.py`, `customer_data.csv`, and output files.

---

## Repository Structure

```
cpc_optimizer/
├── simple_model/          # Weighted-sum LP (v2) — current primary model
│   ├── main.py
│   ├── customer_data.csv
│   ├── allocation_results.csv
│   ├── model_summary.csv
│   └── results.md
├── green_note_sample_main.py   # Blank Lyric Green Note template
└── original_code.py            # Pre-Lyric standalone script (reference only)
```

Future models will follow the same folder pattern.

## Input Data — `customer_data.csv`

Each row is one customer. Columns:

| Column | Type | Description |
|---|---|---|
| `Customer` | string | Customer ID |
| `Quantity` | int | Total demand in MT |
| `$/MT` | float | Gross profit per MT |
| `Alt?` | int 1–4 | How many alternatives the customer has. 1 = sole supplier / no alternatives (high retention risk), 4 = can easily go elsewhere |
| `Strategic?` | int 1–4 | Strategic value. 4 = most strategic |
| `Importance` | int 1–4 | Relationship importance. 4 = most important |
| `Filled` | int | MT already allocated to this customer before this run. The model allocates at most `Quantity − Filled` additional MT |
| `Shutdown_Flag` | 0/1 | 1 = customer faces a production shutdown if unfilled below their floor |
| `Shutdown_Floor_MT` | int | Minimum MT needed to avoid a shutdown. Only relevant when `Shutdown_Flag = 1` |
| `Delay_OK` | 0/1 | 1 = customer can accept a delayed delivery |
| `Goodwill_Risk` | int 1–4 | Risk to the relationship if under-allocated. 4 = highest risk |
| `Contract_Firm` | 0/1 | 1 = customer has a firm contract (delivery is an obligation, not discretionary) |
| `Fwd_12mo_GP_Est` | float | Forward 12-month estimated GP from this customer (used in future models) |
| `Switching_Cost` | int 1–5 | Cost to the customer of switching suppliers. 5 = very high switching cost |

> **Note:** `Shutdown_Flag`, `Shutdown_Floor_MT`, `Delay_OK`, `Goodwill_Risk`, `Contract_Firm`, `Fwd_12mo_GP_Est`, and `Switching_Cost` are present in the data but only used by the more advanced models. The simple model reads only the first eight columns.

## Model — `simple_model/main.py`

### What it does

A weighted-sum linear program that allocates available supply across customers to maximise a composite score. Each customer is scored on four dimensions; the LP fills the highest-scoring customers first up to their remaining demand.

### Objective

Maximise:

```
w_gp  × Σ [ (gp_i / max_gp)   × x_i ]  / total_remaining
w_imp × Σ [ (importance_i / 4) × x_i ]  / total_remaining
w_str × Σ [ (strategic_i / 4)  × x_i ]  / total_remaining
w_alt × Σ [ ((5 - alt_i) / 4)  × x_i ]  / total_remaining
```

Where `x_i` is the new MT allocated to customer `i` this run.

All four terms share the same normaliser (`total_remaining`) so the weights are genuinely comparable — changing `w_gp` from 0.4 to 0.5 has the same unit effect as changing `w_imp` from 0.3 to 0.4.

The `Alt` signal is inverted (`5 - alt`) so customers with fewer alternatives (higher retention risk) score higher.

### Constraints

| Constraint | Description |
|---|---|
| `Σ x_i ≤ supply` | Total allocation cannot exceed available supply |
| `0 ≤ x_i ≤ (Quantity_i − Filled_i)` | Per-customer cap at unfilled remaining demand |

### Parameters

| Parameter | Default | Description |
|---|---|---|
| `supply` | 4000 | Available MT to allocate this run |
| `w_gp` | 0.40 | Weight on gross profit term |
| `w_imp` | 0.30 | Weight on importance term |
| `w_str` | 0.20 | Weight on strategic term |
| `w_alt` | 0.10 | Weight on alt (retention risk) term |

Weights are automatically re-normalised to sum to 1, so you can set them to any positive values (e.g. 4, 3, 2, 1 gives the same result as 0.4, 0.3, 0.2, 0.1).

### Outputs

**`allocation_results.csv`** — one row per customer, sorted by priority rank:

| Column | Description |
|---|---|
| `Priority_Rank` | LP priority order (1 = highest). Because the objective is linear with box constraints, the LP is equivalent to greedy filling in this order |
| `Demand_MT` | Total customer demand |
| `Filled_MT` | Already filled before this run |
| `Remaining_MT` | Demand − Filled (the cap for this run) |
| `Allocated_MT` | MT allocated by this run |
| `Total_Fill_Rate` | (Filled + Allocated) / Demand — cumulative fill rate vs full order |
| `GP_Per_MT` | Gross profit per MT |
| `GP_Allocated` | GP generated by this allocation |
| `GP_Max_Possible` | GP if the full order were filled |
| `Importance / Strategic / Alt` | Input scores |
| `Score_GP/Importance/Strategic/Alt` | Each term's contribution to the objective score |
| `Score_Total` | Sum of the four score components |

**`model_summary.csv`** — single-row run summary:

| Column | Description |
|---|---|
| `Total_Supply` | Supply parameter used |
| `Total_Demand` | Sum of all customer demand |
| `Total_Filled_Before` | Sum of Filled column (pre-run) |
| `Total_Remaining` | Total unfilled demand entering this run |
| `Total_Allocated` | MT allocated (should equal supply if demand ≥ supply) |
| `Supply_Utilisation_Pct` | Allocated / Supply × 100 |
| `Total_GP_Allocated` | Total GP generated |
| `Total_GP_Max_Possible` | GP if all demand were filled |
| `GP_Capture_Pct` | GP_Allocated / GP_Max_Possible × 100 |
| `Objective_Score` | Optimised objective value |
| `w_gp / w_imp / w_str / w_alt` | Normalised weights used |
| `Solver_Status` | HiGHS solver message |

### Tuning the weights

- **Raise `w_gp`** to prioritise revenue — the model will prefer high-margin customers even if they have low strategic or importance scores.
- **Raise `w_imp` or `w_str`** to protect key relationships — customers with top Importance/Strategic scores move up in priority regardless of GP.
- **Raise `w_alt`** to prioritise customers with no alternatives (retention risk) — useful when relationship preservation matters more than short-term GP.

## Running locally

```bash
cd simple_model
python main.py
```

Reads `customer_data.csv` from the same directory, prints results, and writes `allocation_results.csv` and `model_summary.csv`.

## Lyric Studio deployment

Upload the model folder (`simple_model/`) directly to Lyric Studio. The `run(inputs, parameters, configs)` entrypoint, input table name (`customer_data`), and all column names match the Schema tab. The `if __name__ == "__main__"` block is ignored by Lyric and is for local testing only.
